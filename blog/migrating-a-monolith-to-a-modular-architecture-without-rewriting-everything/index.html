Migrating a Monolith to a Modular Architecture Without Rewriting Everything

7 min read · Oct 30, 2026

A pragmatic path from tangled monolith to modular monolith — identifying seams, enforcing boundaries with tests, extracting modules one at a time, and avoiding the rewrite trap that kills so many migrations.

“Do not rewrite. Restructure.” — the first rule of monolith migration

A codebase that has grown for years develops the same kind of entropy: circular dependencies, shared mutable state, and a utils folder that has become a dumping ground. The instinct is to rewrite in a new stack. The evidence says that almost always fails.

This article outlines a quieter path: turn the monolith into a modular monolith first, one boundary at a time.

Identify the Seams

Before you can modularize, you need to know where the natural boundaries are. Draw the dependency graph and look for:

  • Clusters — groups of files that talk mostly to each other
  • Stable hubs — low-level utilities everyone imports
  • Tangled cores — the small set of modules where the real chaos lives

You do not need a perfect architecture diagram. You need five or six plausible module boundaries to start with.

Enforce Boundaries Before Extracting Code

The cheapest way to find a boundary is to declare it and let the compiler enforce it. Add a lint rule that forbids cross-module imports except through a public interface:

Then make every violation a CI failure. The first week produces a long list; the second week produces silence.

Note

A boundary enforced by tooling is a boundary that survives. A boundary enforced by convention survives until the next deadline.

Extract One Module at a Time

Extraction is not a big-bang event. Pick the module with the clearest boundary and move it step by step:

  1. Move the files into modules/<name>/
  2. Give it a public index.ts and make the module self-contained
  3. Move its database access behind a repository interface
  4. Delete the now-dead cross-module imports

Each step is a small, reviewable pull request. Each step leaves the application green.

Let the Data Move Last

The most expensive part of modularization is data. Start with code boundaries while the database stays shared; move ownership of tables only when a module’s code is already clean.

1. DeclareEnforced by lintShared
2. ExtractModule self-containedShared
3. DecoupleRepository interfaceShared
4. SplitClean moduleOwned tables

Warning

Splitting the database too early couples the hardest migration (data) to the most fragile moment (the first extraction). Code first, data later — almost always.

The Metrics That Tell You It Is Working

  • Cross-module imports trending to zero
  • Tests run against module boundaries, not only the whole app
  • A new feature touches exactly one module
  • The utils folder is shrinking, not growing

When a new feature can be built without editing three unrelated modules, the modular monolith has done its job — and you may never need microservices at all.

Conclusion

Rewriting a monolith in a new stack throws away the only thing that has any value: the behavior, the edge cases, and the hard-won knowledge embedded in the existing code.

  • Find the seams
  • Enforce boundaries with tooling
  • Extract one module at a time
  • Move the data last

“Architecture is the decisions you make once and wish you could make again. Migration is the chance to make them deliberately.”

The modular monolith is not a compromise. It is often the best architecture — and the least heroic way to get there.
